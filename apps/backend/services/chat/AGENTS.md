# chat service (TypeScript)

Conversation + agent runtime service. It owns conversation/message/run observability in PostgreSQL and consumes admin (providers), knowledge (documents/artifacts), and executor (durable background tasks) through `@backend/transport-ts`.

## Runtime contract

- The primary Agent uses `@backend/agent-runtime-ts`, shared with the Electron host: one AI SDK v7 `ToolLoopAgent` factory, prompt assembler, step policy, tool manifest/outcome and approval policy. Service code supplies model, catalog, storage and observability adapters; never add a separate local/cloud loop. One POST creates one run.
- The normal safety cap is 50 model steps, with the last step reserved for a truthful no-tool summary. Independent calls emitted by one model response remain concurrent end to end: provider requests set `parallel_tool_calls=true`, AI SDK local execution keeps its default concurrent behavior, and the batch middleware only enforces `load_skill` and Plan/client-tool barriers. Content generation and other dependent side effects remain prompt-serialized.
- Browser disconnect only drops an SSE subscriber. Redis retains a bounded native UIMessage SSE replay buffer only while the run is active so `useChat.resumeStream()` can attach through the GET route. The persistence consumer coalesces raw provider/UIMessage chunks for at most 25 ms or 32 KiB before `XADD`; Redis entry count is a storage-fragment guard, never a model-step or provider-delta limit. The buffer uses a short sliding lease, is deleted after journal finalization, and must abort a run before exceeding its actual byte/entry budget; PostgreSQL remains the terminal message source.
- Executor-backed media tools only submit durable work and return `task_id` immediately. The model-facing tool execution never watches task completion; task status, projections, approvals, and results are read independently from Executor-owned APIs.
- Stop uses the run cancellation endpoint. Propagate the server-owned run `AbortSignal` into model, search, multimodal, and nested artifact model calls.
- Explicit Stop finalizes every unfinished official tool part as `output-error`, persists unfinished todos as `cancelled`, and waits for the local run finalizer before returning. Route cleanup only detaches the stream.
- Replay is a transport concern only: never model it as ToolLoopAgent state or claim process-crash resume. Plans and messages remain durable business context.
- PostgreSQL UIMessage history is the context authority. OpenAI Responses uses native server compaction at 80% of the effective input budget so a single multi-step run stays bounded. Stored continuation is valid only from the immediately preceding journal output on the same provider/model; a lineage whose last model-step input usage reaches that watermark or is unavailable is severed before the next run and rebuilt from the local journal. Unsupported dialects never receive OpenAI-only context fields. Full replay drops opaque provider compaction items and stored item references. Local summary failure fails the run without advancing coverage or silently omitting unsummarized history; usage from completed compaction batches is still recorded.
- `subagents` is an optional inline tool for bounded read-only web investigations that materially benefit from a fresh disposable context or from running 2–3 genuinely independent tasks concurrently. It is not a default research/report router: the primary model chooses it inside the same ReAct loop from the tool description, while the harness performs no intent/difficulty classification or automatic task decomposition. Small, sequential, shared-context, or directly searchable work stays in the primary loop. Each fresh child has only `web_search` and `web_fetch`, receives an explicit bounded task/context instead of parent history or response lineage, streams bounded compact nested progress rather than a cumulative message on every delta, and returns a complete terminal message plus only a compressed final result through `toModelOutput`. Children propagate Stop, record usage independently, cannot approve tools or delegate recursively, and are not durable across process loss.
- `ask_user` is a client tool without `execute`. The browser supplies `addToolOutput`; AI SDK automatically starts the next request. One call batches all currently known independent questions with stable semantic IDs and returns structured answers; dependent follow-ups use later continuations.
- Runtime Bash uses a lazy, real Linux sandbox per run. Chat owns its lifecycle; sandbox owns Docker/gVisor or Kubernetes execution and deadlines. Chat restores conversation files at stable writable `/workspace` paths and automatically snapshots changed/new/deleted business files to immutable Storage revisions before teardown; original external attachments remain read-only under `/workspace/sources`. `upload_artifacts` batch-publishes completed workspace files as durable Chat/Storage identities and is not the workspace persistence boundary. Egress uses an operator-controlled proxy; no business credentials enter guests. Code Mode uses the AI SDK local tool-caller path with a cache-stable conversation catalog and may orchestrate only explicitly eligible public `web_search` / `web_fetch` reads; both remain directly callable. Prefer direct search/fetch for one request, Code Mode for multiple public reads with programmatic reduction, subagents only for fresh-context investigations, and Bash for files/CLI/raw responses. Code Mode runs in QuickJS, not the Linux guest, has a 90-second wall-time budget, requires every nested call to be awaited, and returns corrective guidance for common runtime failures. Bash, private context, approvals and business side effects remain direct tools.
- Trace persistence is observability and must never fail generation.
- Application tools return a ToolOutcome. SDK `toolSearch()` retains its native result so deferred definitions can activate. Business failures stay `output-available` for UI/persistence and map to AI SDK `error-json` through `toModelOutput` for the primary LLM; Abort, Stop, approval denial, invalid input, and protocol failures retain native control flow. Full failed outcomes persist in `output_json` with a readable error summary. Do not add automatic retry to the wrapper.
- Built-in function tools use schema field descriptions, strict calling, and compact input examples instead of duplicating payload contracts in the system prompt. `repairToolCall` records invalid names/inputs and returns `null`; it must not invoke a hidden repair model or rewrite arguments. The primary agent receives the native rejection and may correct the call in its next step.
- Tool data and progress schemas contain domain payload only. Use `toolCompleted`, `toolRunning`, `toolPartial`, `toolBlocked`, or `toolFailed`; never repeat protocol-level `ok/status` inside `data` or `progress`.
- The UIMessage SSE stream is a cross-stack contract. Before adding any custom `data-*` part / streamed field, read `schemas/streaming/chat-uimessage-stream.md` and register it there. Reuse official parts first (`text`/`reasoning`/`tool-*`/`file`/`source-*`, message `metadata`); only invent a `data-*` part when none fits (a custom part that duplicates an official one is a bug).

## Tools and artifacts

- Tool orchestration (see `docs/ADR/agent-runtime.md`): **thin harness — no general runtime scheduler or lock.** The SDK owns the tool loop; `prepareStep` only applies the final-step truthful-summary bound. The middleware makes `load_skill` a batch barrier and keeps `ask_user` exclusive; independent read-only research/context calls may retain native same-step concurrency. Content generation is prompt-serialized: never co-emit `bash`, `upload_artifacts`, `generate_images`, or `create_video_production` with another generation call; observe each generation result before starting the next deliverable. Todos remain optional for substantial multi-item work, are skipped for a single deliverable, and are updated alone between serial deliverables with at most one item `in_progress`.
- Plan mode creates a complete `*-plan.md` with Bash and publishes it in one `upload_artifacts` batch. Chat classifies that stable conversation file as a Plan and records `active_plan_file_id`.
- `update_todos` (normal/agent execution mode only) is a stateless, side-effect-free full replacement of `{id, content, status, deliverable?}`. It has no context state, knowledge writes, revision/CAS, or routing advice. At most one item may be `in_progress`. The optional deliverable tag links the active todo to its official artifact/image/video tool part; for durable media, that part becomes terminal when submission succeeds, not when generation finishes. The next `update_todos` call marks that item terminal and advances at most one pending item.
- The first Bash call restores current Chat-owned files/Plans at their authoritative writable paths and imports original document attachments under read-only `/workspace/sources`. Bash performs discovery and edits. `refresh_conversation_sources` imports only external sources another tool adds or updates later in the same run; workspace persistence does not depend on a model tool call.
- A user save during an active cloud instance acquires the guest workspace edit fence only between commands, validates the editor ETag and on-disk digest, updates that same path, and commits Storage/Chat before releasing execution. Busy writers preserve the draft with `workspace_busy`; the next controlled model step receives changed paths and must re-read them.
- Inline `subagents` offloads one bounded investigation or two to three genuinely independent investigations without taking ownership of the user's intent, synthesis or planning authority. File authoring remains in the primary run Sandbox.
- HTML remains a complete browser artifact and may use scripts, modules, dynamic DOM, Canvas/SVG/WebGL, forms, media, workers, and external runtimes. Capability is never inferred from page count. Preview uses an ordinary iframe without a sandbox capability allow-list; the host must not rewrite, sanitize, or selectively disable browser features.
- Chart-bearing HTML defaults to complete LLM-authored ECharts options and initialization. The document owns one cached Promise loader that tries the pinned platform ECharts 6.1.0 runtime first and the pinned jsDelivr asset as a sequential fallback. Every candidate uses anonymous CORS, SRI and no-referrer before setting src; all ECharts APIs, including theme/map registration, execute after the Promise resolves. This fixed loader behavior is an authoring contract, not a per-request benchmark: normal runs do not download ECharts, recompute its supplied SRI, install browser-test packages or build a loader-only harness solely to retest it. Validate artifact-specific data, options, syntax and interactions, and use an already-available browser when practical. Chart panels use elastic Grid/Flex layouts, but long grids retain content-appropriate minimum track heights and scroll instead of squeezing every row into one viewport. Each logical chart owns one DOM container; instances are registered at creation, observe their own container with `ResizeObserver`, resize after the first layout frame, and use window resize only as fallback. This is an authoring contract for published files, not a compiler, chart DSL, host rewrite, or automatic hydration layer.
- Read and edit the restored authoritative workspace path directly. Include every completed deliverable in one `upload_artifacts` call; use update only to preserve an existing file identity and create only for a new deliverable. A stale ETag or path generation fails closed and never overwrites a newer user edit.
- `generate_images` and `create_video_production` mean “submit a durable generation task”, not “wait for generated media”. They return the Executor `task_id` as soon as the task is accepted; video also exposes that stable ID as `production_id`. Executor owns later planning, provider calls, approvals, persistence, and failure state. A tagged media todo completes when submission succeeds.
- A normal-mode run carrying `data-plan-execution` identifies one stable Chat `file_id`; resolve its authoritative path from `/workspace/sources/workspace-manifest.json` and read it completely before execution. A natural-language request to execute a Plan remains an agent decision: inspect `*-plan.md` files with Bash, then use `ask_user` when multiple Plans exist. The projector never injects an active Plan or candidate list.
- Every run re-resolves mutable authoritative references it uses: the selected Plan’s current revision from Chat's conversation-file registry, activated Skill from Admin's latest published snapshot, and any referenced instruction/config file from its owner. Prior read/load outputs are not caches. Successful search outputs are historical evidence and must not be repeated unless the user explicitly requests refreshed or latest evidence.
- `web_search` uses Exa Search as the primary source (`POST https://api.exa.ai/search`, `x-api-key`) and Tavily Search as fallback (`POST https://api.tavily.com/search`, `Authorization: Bearer`). Freshness is handled two ways so the model never falls back to its training-cutoff year: (1) the current date is injected into the agent instructions as a trailing `<environment>` block (single source of truth — `renderEnvironment` in `@backend/agent-runtime-ts/instructions/assembler`, assembled last so the static prompt prefix stays cache-stable); (2) the tool keeps its own `category`/`time_range`/`start_date`/`end_date` inputs so recency is a structured, server-side filter rather than a year stuffed into the query. Exa freshness uses two distinct levers together: `startPublishedDate`/`endPublishedDate` bias WHICH results return (by publish date; from an explicit range or derived from `time_range`), while `maxAgeHours` (derived from `time_range`: day/week/month/year → 24/168/744/8760) forces a livecrawl of stale page CONTENT. `category` maps to Exa `news`/`research paper` (and to Tavily's `topic`). Snippets prefer Exa `highlights` (token-efficient); the heavier whole-page `summary` is requested only for `research_paper`. If Exa fails or returns no results and `TAVILY_API_KEY` is configured, the tool falls back to Tavily `search_depth: "advanced"`; Tavily is optional (Exa is primary). `create_memory`/`update_memory` stage a candidate; user approval remains asynchronous in the memory panel.
- Built-ins are grouped by capability under `tools/builtins/` but remain one flat AI SDK ToolSet. `manifest.ts` is the source of tool policy, planning capability projection, and UI metadata. Plan mode receives only callable research/planning tools plus a generated summary of execution capabilities.
- Executor task submission lives in `agent/tasks/executor-task.ts`; completion watching is intentionally outside the model-facing tool boundary.

## Boundaries

- No direct imports from another service.
- Redis clients are created only through `infrastructure/redis`: ordinary commands share `getRedisClient()`, blocking stream reads use `duplicate()`, and readiness probes use an isolated client from `createRedisClient()`.
- Service URLs, internal auth, DTOs and timeouts live in transport-ts clients; chat-local clients only add cache/error mapping.
- User identity belongs to iam, provider configuration to admin, semantic documents to knowledge, conversation file references to chat, and durable bytes/delivery to storage.
- DB transactions (docs/ADR/architecture.md): multi-step / multi-table writes use `getDb().transaction(async (tx) => ...)` (auto commit/rollback), threading `tx` through every read/write; single-statement writes stay bare. Run journal finalization commits tool outcomes, message/metadata, run status, selected leaf and lease together. Claim and finalization lock conversation before run; terminal run states cannot be overwritten by late cleanup. External effects, including Redis stream-pointer cleanup, stay outside the transaction and compare run identity.

- `src/application/agent/agents/tool-loop.ts` — ToolLoopAgent implementation
