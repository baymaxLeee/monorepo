# ADR 0032: Code-governed prompt layering and structured Bot profile

## Status

Accepted. Supersedes ADR-0026 decisions 4–6 (free-text `system_prompt` /
`<agent_persona>`); refines ADR-0011 (ToolLoopAgent core) and the Skill
instruction channel without changing the single-agent runtime. ADR-0041 later
removes dynamic conversation state from the instruction layer.

## Context

Chat assembled the agent's system instructions as a monolithic string, and the
bot persona was a free-text `bots.system_prompt` (up to 20,000 chars, ADR-0026).
That value flowed admin → `ResolvedAgent.system_prompt` → chat → straight into
`ToolLoopAgent.instructions` as a first-class `<agent_persona>` section. Two more
free-text channels existed: `tool-loop.ts` appended `resolvedTools.instructions`
(a raw `string[]`) after the prompt, and agent extensions could contribute an
arbitrary `AgentExtensionContribution.instructions?: string[]`.

Reviewed against how Claude Code / Codex / Cursor construct prompts, this shape
had three problems:

1. **Operator-authored free text became system instruction.** An admin editing a
   textarea gained the expressive power of the model's constitution. Wrapping it
   in a tag and adding "do not override" copy is not a security boundary — the
   text sits in the same channel as the safety/capability rules.
2. **No structure, no audit.** A single blob cannot be diffed, versioned, or
   reasoned about section-by-section; escaping and trust boundaries were ad hoc.
3. **Multiple raw injection seams.** `instructions: string[]` from tools and from
   extensions let any contributor append unescaped text to the final prompt.

The runtime premise is fixed (ADR-0011, ADR-0028): there is exactly **one**
general `ToolLoopAgent`; bots differ only by upper-layer assembly (skills, MCP,
and a small structured role description), never by per-bot hard-coded tools.

This is the demo phase, so per the repo's future-first policy we cut straight to
the target shape with no compatibility shim: historical `system_prompt` values
are discarded, not migrated into the new fields.

## Decision

1. **One code-owned, fixed-order XML assembler.** All instructions are composed
   in `agent/context/instructions/assembler.ts` into a single
   `<agent_instructions>` document. Section order is code-owned and
   cannot be reordered by callers; trust decreases top→bottom:

   ```
   core_policy → runtime_contract → execution_protocol → capability_contract →
   available_skills → activated_skill → bot_profile → user_memory_data → environment
   ```

   `core_policy` / `runtime_contract` are code constants; `capability_contract`
   is code-generated from the run's resolved tool manifests (plan mode only);
   `environment` (server date) stays last so the static prefix stays cacheable.

2. **`system_prompt` is deleted end-to-end; admin owns a structured Bot
   profile.** Admin migration `v1.9.0.sql` drops `bots.system_prompt` and adds
   `role_description`, `domain_description`, `audience`, `tone` (enum:
   professional / concise / friendly / empathetic), `welcome_message`, and
   `suggested_questions` (jsonb). Pydantic enforces length limits, the tone enum,
   array count, and control-character rejection — admin can describe identity but
   can no longer author raw system instructions.

3. **Only model-relevant identity enters the model.** Internal `ResolvedAgent`
   carries `name`, `role_description`, `domain_description`, `audience`, `tone`.
   `welcome_message` and `suggested_questions` are UI-only presentation copy,
   served through the public Bot API and deliberately excluded from
   `ResolvedAgent`, so they never reach the model context.

4. **The prompt renders schema-bound fields only, always escaped.** chat's
   `getAgent` builds a read-only `BotProfileSnapshot`; it flows
   `routes/agents.ts` → `RunAgentInput.botProfile` → `loadInstructionContext` →
   the assembler, which renders `<bot_profile>` from structured leaves via
   `xml.ts` escaping. When a bot has no structured identity yet, `<bot_profile>`
   is simply omitted. As revised by ADR-0041, the projector does not discover or
   inject Todo, active-Plan, or document business state. Only actual message
   parts, required protocol conversion, and bounded history compaction enter
   model messages; approved memory remains low-authority instruction data.

5. **The thin router is structured-only; every raw-string seam is removed.**
   `ToolCatalog.resolve()` returns a typed `InstructionContributions`:
   `capabilities?: string` (code-generated) and `skills?: SkillListing[]`
   (structured `{name, description}`). `<available_skills>` is generated by the
   renderer from `SkillListing[]` (name/description escaped), replacing the old
   free-text `workflow: string[]` / `<workflow_guidance>`. The extension seam's
   `AgentExtensionContribution.instructions?: string[]` is deleted. There is now
   **no free-text instruction channel** anywhere below `core_policy`; a future
   skill/MCP integration contributes typed data, never a raw prompt string.

6. **Hardcut, no compatibility layer.** No dual-write, no legacy read path, no
   `legacyPersona` bridge. The oncall bot's full RCA workflow is not stuffed back
   into free text; its seed keeps a *condensed* structured `role_description`, and
   the complete four-part workflow moves to a code-versioned Skill (ADR-0028)
   later. The oncall bot's behavior is intentionally "thinner" during the
   transition.

7. **One code-owned execution protocol.** The static
   `<execution_protocol>` sits after the mode-specific runtime contract and
   before dynamic capabilities, Skills, Bot configuration, and context data. It
   defines the primary agent's per-step loop: orient → route context → route
   Skills → check sufficiency → choose action → execute → observe → continue or
   stop. Tool schemas remain the input contract, manifests remain the mode and
   permission boundary, and deterministic HTML repair remains enforced by AI
   SDK `prepareStep`; the prompt does not become a second scheduler.

Scope boundary: this ADR governs prompt **layering** and the structured Bot
profile. The **management and assembly** of skills / MCP / sub-agents remains
future work (`docs/plans/agent-extensions-mcp-skill-subagent.md`); this change
only narrows their injection seam to a typed contract.

## Consequences

- The model's constitution, capability boundary, and trust ordering are pure
  code. Operators configure identity through discrete, validated fields and a
  fixed tone enum — never a raw system prompt.
- The final prompt has a stable XML root and fixed layers; all admin/user text is
  escaped and confined to its section. The running code is the sole prompt
  definition; no prompt schema version or compatibility branch exists.
- The execution protocol connects context, Skills, tools, and completion in one
  explicit primary-agent loop without adding role-play agents or manual tool-loop
  code.
- Tools, memory, documents, and retrieval results are all data/untrusted context;
  no component can promote them into the instruction layer.
- **Destructive, by design:** existing `system_prompt` content is lost. Bots show
  no persona until their structured profile is filled in. The schema cutover is
  defined by `admin/migrations/versions/v1.9.0.sql`; applying it (and populating
  bot profiles) is an operator action.
- Chat MFE consumption of `welcome_message` / `suggested_questions` in the empty
  conversation experience is deferred additive work; the fields are stored and
  served today.
- No test scaffolding is added (demo phase). Contract regeneration ran for admin
  OpenAPI → transport-ts → frontend typed client.
