# ADR-0029: 业务库从 MySQL 整合到共享 PostgreSQL

## Status

Accepted — 2026-07-06(分支 `agent/pg-consolidation/main`,基线 `9405922`)

> `0028` 已被 field-support system skill ADR 占用。本迁移使用 `0029`,并基于
> `main@9405922` 完成。

## Context

当前后端同时运行两种关系型引擎:

- **MySQL 8.4**(容器 `monorepo-mysql`):6 个业务库 `gateway` / `iam` /
  `admin` / `telemetry` / `chat` / `executor` 各一个 database。
- **PostgreSQL 16 + pgvector**(容器 `monorepo-workflow-postgres`,镜像
  `pgvector/pgvector:pg16`):承载 executor 的 Workflow DevKit World(`workflow`
  库)与 knowledge 服务(`knowledge` 库,含 pgvector 向量)。knowledge 早前已
  从 MySQL 迁到此实例,PG migration 路径已验证;整合后 `db-migrate.sh` 只支持
  PostgreSQL,不再需要逐服务 engine marker。
- **Redis 7**:gateway / admin / chat 的缓存/会话,与本决策无关,保持不变。

single-VPS 有 <1GB RAM 预算(`docker-compose.prod.yml` 已把 MySQL
`innodb-buffer-pool` 压到 256M)。同时维护两套 RDBMS 在内存、备份、监控、迁移
路径上都是双份成本。`docker-compose.yml` 注释亦记录 "full MySQL→PG
consolidation of other services is a separate later task"。

各服务对 MySQL 的耦合很浅(实测):

- **gateway** 无业务表(`internal/infrastructure/store/store.go` 仅启动 Ping,无任何裸 SQL),
  本质无状态。
- **iam** 走 GORM,业务代码方言无关(`OnConflict`/`Locking`/`AutoMigrate` 由
  GORM 生成);唯一硬编码点是靠错误字符串匹配唯一约束名。
- **admin / telemetry** 走 SQLAlchemy 2.0 async(`asyncmy`);唯一 MySQL 方言点
  是 telemetry 的 `INSERT ... ON DUPLICATE KEY UPDATE`。
- **chat / executor** 走 Drizzle `mysql2`;chat 有 4 处 `onDuplicateKeyUpdate`,
  executor 用 try-insert / catch 做幂等。

## Decision

将 6 个业务库迁移到已存在的 PG 实例,彻底移除 MySQL。实例**保留
`workflow-postgres` 名字不变**——`docker-compose.yml` 注释已刻意如此以避免
re-wire executor 的 Workflow World env;正名为 `postgres` 纯 cosmetic 却会牵动
高风险的 Workflow World 连接、并扩大与并行 org-rbac 分支的冲突面,故降级为
可选 follow-up(见"边界")。

### 不可变迁移规则

1. **无历史数据迁移**:本地与 single-vps 的数据库 / volume 直接重建,是
   **破坏性**操作;不得用于需保留数据的环境。
2. **直接切换**:删除 MySQL 容器、驱动、配置与运行路径,不保留双写、灰度或兼容
   分支。服务必须完成 build/lint + 空库全量迁移 + 业务 smoke 后交付。
3. **服务级权限隔离**:每个业务 database 由同名非超级登录 role 拥有,应用只能
   使用自己的 role。`workflow` 超级用户只负责实例 bootstrap 与 Workflow World;
   `PUBLIC` 不保留 database 权限或 public schema 的 CREATE 权限。
4. **单一迁移实现**:所有业务库统一走 `scripts/db-migrate.sh`;每个 migration 文件在
   **单事务**内执行并**原子更新** `migration.version`(失败则 schema 与版本一起
   回滚);扩展安装是 bootstrap 职责,且**仅 `knowledge` 库**安装 `vector`。
5. **生产 db-init 走网络**:single-vps 的 db-init 改为 PG client migration image,
   通过网络连 `postgres`,不挂 docker socket、不复用依赖 `docker exec` 的本地
   脚本;合并现有 `knowledge-db-init`,保留 `workflow-db-init` 跑官方 setup。
6. **最终 schema 对齐**:每个服务完成后,对比"空库执行全部 migration"的实际
   schema 与 ORM 模型 / 约束 / 索引,不只靠查找替换方言。
7. **不新增测试脚手架**:遵守 demo 阶段规则,仅跑既有 lint/build + 手工/API smoke。

### 连接池预算

单实例合并后连接数成为真实约束。各服务峰值连接(按当前配置):

- iam(GORM `SetMaxOpenConns`):8
- admin(SQLAlchemy pool 5 + overflow 10):15
- telemetry(同上):15
- chat(`postgres-js`,对齐现 `connectionLimit`):8
- executor(同上):8
- knowledge(SQLAlchemy,已在 PG):15
- Workflow World(graphile-worker):约 10
- gateway:0(迁移后无 DB)

峰值合计约 **79**,PG 默认 `max_connections=100`,余量约 18。demo / 单副本够用;
**k8s 多副本会翻倍超限**,需调高 `max_connections` 或引入 PgBouncer(记录为
follow-up,不在本次实现)。

### 迁移基线(`9405922`,含 org-rbac)

各服务重写的 MySQL migration 数:**iam 4**(`v1.0.0`–`v1.3.0`)、admin 9
(–`v1.8.0`)、chat 14(–`v2.2.0`)、executor 2、telemetry 1、gateway 1;
knowledge 的 6 个 PG migrations 不改 SQL 语义。共 **26 个 MySQL SQL 文件**
完成翻译。

**迁移文件策略——逐文件翻译、保留版本演进(不 squash 成单 baseline)**:目标虽是
全新 PG 库、理论上可把每个服务压成一个 baseline,但压缩需要"人肉合成最终 schema"
的全局推理(chat 14 步累积尤甚),易漏 ALTER;逐文件翻译是**局部、规则化**的机械
映射,风险最低,且不动现有 `db-migrate.sh` 版本表 / seed / 版本连续性语义。空库上
的 backfill/数据订正语句为无害 no-op。每服务翻完后按规则 6 对齐最终 schema。

### MySQL→PostgreSQL SQL 翻译规则(所有服务共用)

| MySQL | PostgreSQL | 备注 |
|---|---|---|
| `` `ident` `` 反引号 | 去掉(或 `"ident"`) | 保留字才需双引号 |
| `TINYINT`(主键/枚举) | `smallint` | |
| `tinyint(1)` 布尔 | `boolean` | `DEFAULT 0/1`→`false/true`;CHECK 内 `=0/1`→`=false/true` |
| `datetime`/`datetime(6)` | `timestamptz`(默认) / `timestamp`(ORM 显式 naive) | 默认带时区更安全;telemetry 事件表 ORM 声明 `DateTime(timezone=False)`,故用 `timestamp(3)` 保持 ORM↔schema 一致 |
| `char(26)`(ULID) | `char(26)` | 定长 ULID 无 padding 问题,保留 |
| `json` | `jsonb` | |
| `mediumtext`/`longtext` | `text` | |
| `bigint UNSIGNED` | `bigint` | PG 无 UNSIGNED;计数列非负由应用/CHECK 保证 |
| `AUTO_INCREMENT` | `generated by default as identity` | 用 `BY DEFAULT` 而非 `ALWAYS`:匹配 MySQL 可显式插入语义,兼容 dump/restore |
| `ENGINE=/CHARSET=/COLLATE=` | 删除 | |
| `COMMENT '...'`(内联) | 删除 | demo 阶段不迁列注释 |
| `UNIQUE KEY name (col)`(建表内) | `CONSTRAINT name UNIQUE (col)` | |
| `KEY name (col)`(建表内普通索引) | 表外 `CREATE INDEX name ON t (col)` | PG 建表体不能定义非唯一索引 |
| `ALTER TABLE ADD KEY` | `CREATE INDEX` | 同上 |
| `ADD COLUMN ... AFTER x` | 去掉 `AFTER x` | PG 无列序 |
| `INSERT IGNORE` | `INSERT ... ON CONFLICT DO NOTHING` | |
| `INSERT ... ON DUPLICATE KEY UPDATE` | `INSERT ... ON CONFLICT (col) DO UPDATE SET ...` | 需显式冲突目标列 |
| `DELETE a FROM a JOIN b ...`(多表) | `DELETE FROM a USING b WHERE ...` | |
| `NOW()` | `NOW()` | 兼容,保留 |

## Consequences

- 少一个 RDBMS:内存、备份、监控、迁移路径均收敛到单引擎。
- 统一 SQL 方言与 JSONB / `ON CONFLICT` / pgvector 能力,契合 AI-Native 定位。
- 应用层方言改动少:telemetry 1 处 + chat 4 处 upsert 改 `ON CONFLICT`;iam 改
  唯一冲突判定为 SQLSTATE `23505` + 约束名;iam GORM 业务代码零改。
- org-rbac 已合入基线,iam 迁移直接覆盖其 `v1.2.0`/`v1.3.0` 与扩表后的
  `store.go`;不再有并行分支 merge 冲突,基线即最新业务代码。

## 迁移顺序

Phase 0 基线 + ADR → Phase 1 PG 基础设施、独立 role 与统一迁移器 → Phase 2
gateway 去 DB → Phase 3 iam → Phase 4 admin + telemetry → Phase 5 chat + executor
→ Phase 6 删除 MySQL + 全链路回归。

## 边界

- workflow World 与 knowledge 保持不动(本就在 PG)。
- 不引入跨库 join;微服务"各库自治"边界不变。
- 容器正名(`workflow-postgres`→`postgres`)、PgBouncer、`max_connections` 调优为
  独立 follow-up,不改变当前 database/role 边界。

## 回退

本项目处于 demo 阶段且数据可重建,不保留 MySQL 回退路径。失败时修复 PostgreSQL
实现并重新创建相应 database。
